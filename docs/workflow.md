# 开发流程：规格驱动，怎么改、怎么验、怎么记

> 答什么：一件活（新功能、改已有功能、修 bug、接新材料、改提示词）从头到尾按什么顺序做；规格怎么写、怎么改版；每种东西拿什么工具验、看哪个数、什么时候跑。
> 谁何时读：接手时读一遍；每开一件活对一下「一件活从头到尾」；要说「验过了」之前翻「验证」。
> 怎么变短：规矩的来历不写在这里（在《AI 编程项目管理指南》和 `docs/lessons.md`）；某个模块的验收细则住它的规格，这里只写方法和工具。

## 一句话

先改规格，再改代码，再验证，最后记账。规格（`specs/`）是「要做成什么」的唯一出处：代码和规格对不上时，要么改代码，要么先跟 owner 对齐后改规格，不许让两边各说各的。

## 一件活从头到尾

### 新需求、新功能

1. **读 owner 的话**：分成拍板 / 待议 / 顾虑。他常用语音输入，长句可能有两种读法；管产品方向的，先用一句话复述「我理解成 A，对吗」再动手（`docs/lessons.md`：误解过一次，白做了一轮）。
2. **找它归哪份规格**：看 `specs/SPEC-000-overview.md`「模块和规格」。没有合适的就开新号（接着往下编），从 `specs/SPEC-template.md` 起步，并在 SPEC-000 的模块表里加一行。
3. **先对话再写**：复述目标 → 3 到 5 道选择题（选项互斥、标推荐、写代价）→ owner 拍完再落规格。工程细节自己拍，产品方向必问，明摆着要做的直接做。
4. **写规格**：每条规则配一条验收（格式见下一节）；答不出怎么验的，先补观察手段。值不值两栏写清好处和代价。决策写三件套（结论 · 理由 · 排除了什么）进 `docs/decisions.md`，同样的理由写进它管的那段代码的头注释。
5. **说不准的环节先实验**：拿真实数据做最小实验，把输入和输出给 owner 看，再定方案、写代码。例：音标从词表取还是让模型写，先拿 45 个词比了再定（SPEC-006）。
6. **写代码**：头注释引规格编号和决策编号，写「为什么」。
7. **验证**：见「验证」。新规则的自动检查，用例名以验收编号开头。
8. **记账、提交**：见「记账」。
9. **交给 owner 试**：`pipeline/stable_copy.py invite --what "<这一版多了什么>"` 钉一版，跟他说「可以更新了」，他点页面上的「更新」（`specs/SPEC-008-stable-and-dev.md` 操作手册）。他的反馈回到第 1 步，按「改已有的功能」走。

### 改已有的功能（优化、owner 试用后的反馈）

- 先改规格：规则表里直接改成新规则，旧规则不留在表里；文末「改版记录」加一节——日期、owner 的反馈要点、改了什么、为什么、代价。
- 被推翻的决策在 `docs/decisions.md` 标「作废」或「部分作废」，写一句为什么，不删。
- 验收项跟着改，自动检查的用例名跟着改。
- 已交付的功能再改，状态回到「开发中」，直到再发出去。

### 修 bug

用户能感觉到的 bug 一律修，不叫「优化」。

1. 先搜 `docs/lessons.md` 有没有踩过。
2. 找根因四步：分类 → 戴科学家帽（先问必然还是偶然，别凭两三个样本定根因）→ 复现 → 对照实验。复现不出就别动代码。
3. 修完，加一道能抓住它的检查，当场改坏一次，确认它真的报错。
4. `docs/lessons.md` 记一条：症状（贴真实报错字眼）、根因、修法、怎么确认修好了。

### 接一份新材料

照 `specs/SPEC-002-prep-pipeline.md`「接一份新材料：操作手册」做，每一步的数记进交接页。

### 改给大模型的提示词

- 只有真跑真模型、读它真写出来的东西才算验过；静态读提示词不算。
- 改完抽查（`pipeline/explain.py sample`，或者重跑那一步再通读输出），发现一类错就改提示词重生成，不逐条手改（SPEC-000 R4）。
- 改那一行的规则后 `teach.py <课> --renote`；改展开的规则后删 `lessons/<课>/explain_cache.json`。

## 规格怎么写、怎么改版

- 文件名 `SPEC-<三位编号>-<英文短名>.md`。开头五行：答什么 · 谁何时读 · 怎么变短 · 状态 · 需求出处。
- 状态只有四个：草稿 / 开发中 / 已交付 / 作废。已交付 = 发出去且有人在用。
- 规则表三列：编号 R1、R2……｜规则｜怎么验收。规则写成能验的行为和数，不写「体验好」这种抽象词。
- 验收编号：
  - A 开头的（A7、A25c、A-next……）是 `tests/test_player.py`、`tests/test_stable_copy.py` 里的自动检查，用例名以编号开头。
  - 写「（人工）」的要人来做，写清做什么、看什么。
  - 用别的工具验的，写清工具和看哪个数（如「`tests/test_audio.py`：结尾 89/89」）。
  - 编号全仓唯一，删了不复用。`tests/test_docs.py` 会核对：每个自动检查都在某份规格里写着；规格里没标人工的 A 编号，测试里都有。
- 规则编号不复用；搬到别的规格的，在原规格留一张「搬走的规则」表写去向（例：SPEC-001）。
- 一个事实只住一处：细则住它的规格，别处引用写「文件名 + 小节名」或「规格号 + 规则号」，不抄一遍。
- 改版记录一版一节，长到翻不动时整批搬到 specs 下新建的 history 文件夹，规格里留一行指过去。

## 验证

### 验什么、用什么

| 验什么 | 用什么 | 什么时候跑 | 多久 · 多少钱 | 看什么 |
|---|---|---|---|---|
| 播放器的行为 | `tests/test_player.py`：Playwright 真的开浏览器、真的点按钮、真的看音频播到第几秒、音量有没有渐弱到零 | 改完 `web/` 或本地服务**必跑** | 不到 1 分钟；点「展开」会真调一次模型，几厘钱 | 最后一行「通过 N 项，未通过 0 项」；没过的看名字前的编号，回规格找规则 |
| 界面看起来对不对 | `tests/test_player.py --shots <目录>` 存关键画面的截图，亲眼看；`--show` 能看见点击过程 | 改了界面 | 同上 | 布局、对齐、字体（音标、中文有没有东拼西凑）、卡片挡没挡住东西、暗色下看不看得清。标准是 frontend-design（owner 2026-09-21 要求）。现在只截 1600×900，做平板适配时加别的宽度 |
| 声音 | `tests/test_audio.py`：录下真的 Chrome 放出来的声音 → 和原音频逐个采样比对，算出实际放的是哪一秒到哪一秒 → 机器耳朵听第一个、最后一个词 → 出试听页 | 改了句子边界、播放器的停法、音频格式 | 约 5 分钟、几分钱 | 放出来的和预定的差不到 50 毫秒；开头、结尾机器听对了几句（第一集 82/89、89/89）；机器说不对的，打开试听页人耳听（SPEC-004 R7） |
| 句子边界干不干净（只看音量） | `pipeline/measure_bounds.py [旧的 lesson.json] [课]` | 调边界前后各跑一次比较 | 几秒 | 句末多播 20/40/80 毫秒能听到声音的交界、句首前很响的交界各几处。会被 k、t、p 骗，只作参考 |
| 备课每一步 | 各步的报告和打印（`align_report.md`、`bounds_report.md`、`ear_report.md`、`teach.py` 打印的分段和覆盖数） | 每接一集 | 随备课 | SPEC-002 操作手册里每一步列的数，和第一集比 |
| 模型写的内容 | `pipeline/explain.py sample <课> <句数> --more`；翻 `lesson.json` 里的 `zh`、`sections`、`notes` | 改了提示词；每换一批材料 | 一次几秒、几厘钱 | 通读：意思对不对、有没有复述句子、音标是不是英音、词组认没认出来。发现一类错改提示词 |
| 朗读 | `pipeline/tts.py check` 出抽听页，机器耳朵听着不对的排前面 | 每集建完（可选）；owner 说某个词读得不对 | 一两分钟、几分钱 | 人耳听；机器耳朵单听一个词不可靠，只用来排先后 |
| 换版本 | `tests/test_stable_copy.py`：临时目录里造真的仓库和体验版，真的切版本、真的起服务、真的走一遍「点更新 → 停 → 换 → 起回来」 | 改了 `pipeline/stable_copy.py`、`pipeline/serve.py`、`start-player.bat` | 约半分钟、不连网 | 「通过 N 项，未通过 0 项」 |
| 文档和代码对不对得上 | `tests/test_docs.py` | 改了文档、加删文件、改了课程文件格式 | 不到 1 秒、不连网 | 全部通过：文档里写到的文件都在；代码文件都写进了 `docs/architecture.md`；自动检查的编号和规格对得上；课程文件的字段都在 |
| owner 的眼和耳 | 播放器「全文」里点 20 句听开头结尾；孩子自己用一集 | 每一版交给 owner 之前钉好（`stable_copy.py invite`），他点「更新」就是新的 | — | 只有人做得出的：听着对不对、孩子用得顺不顺 |

### 什么时候跑什么

- 改了什么就跑跟它相关的那一份，随时跑；三份一起的全套要攒一批向 owner 申请（CLAUDE.md 红线）。
- 说「验过了」之前，能把改前错的和改后对的并排摆出来：一个真数字、一张截图、一段录音。摆不出不许说解决了。
- 会报错的检查写完当场改坏一次，确认它真报错、报的是它。
- 检查的期望值在测试里写死，不从被检查的东西里取。

### 这个项目踩过的假绿

| 看着通过了 | 其实 | 现在怎么验 |
|---|---|---|
| 播放器报告播到第几秒，和算好的切口对得上 | 从没听过放出来的声音；owner 两次听出单词原声带杂音 | 录下放出来的声音听（`tests/test_audio.py`） |
| 切口处很安静 | k、t、p 发音前嘴先闭住，安静的地方在词中间 | 听切下来的是不是那几个词；拿不准的给 owner 听 |
| 机器耳朵说听到了 | 它很宽容，-ugar 也听成 Sugar；被限流时返回的不是结果；换个采样率结论就变 | 听到了还要按音量找真正开口处；机器只挑可疑的，拍板靠人耳 |
| 页面上那个元素在 | 字体缺字、卡片挡住中文，元素照样「在」 | 截图亲眼看；有明确规则的写成位置、字体的自动检查（A7e、A7t） |
| 测试里的桩函数被调了一次 | Playwright 的 `evaluate` 字符串最后一个表达式是函数，它会去调 | 字符串末尾加 `; 0`（`docs/lessons.md`） |

## 记账

每有进展当场做（节奏见 CLAUDE.md「节奏」）：

| 什么变了 | 改哪 |
|---|---|
| 要做成什么、验收标准 | 那份规格的规则表；改版的来龙去脉进它的「改版记录」 |
| 为什么这么选、排除了什么 | `docs/decisions.md`，同样的理由写进代码头注释 |
| 踩了坑 | `docs/lessons.md` |
| 还欠什么、下一件动哪个 | `docs/debts.md` |
| 现在在哪、上一段为什么这么改 | `docs/handoff.md` |
| 加删文件、改了文件格式、接了新的外部服务 | `docs/architecture.md`，改完跑 `tests/test_docs.py` |
| owner 的原话需求变了 | `demand.md` |
| 装了新包、换了工具、端口 | `docs/environment.md` |

提交写做了什么和为什么；几个会话同时干活时带上文件列表。压缩上下文之前敲 `/warp`。
