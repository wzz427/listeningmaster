# 怎么向 owner 汇报

> 答什么：发给 owner 的汇报怎么写他才看得懂，特别是干完一段活之后的总结性汇报怎么编排；发出去之前怎么自检、怎么复核。
> 谁何时读：任何会话在发出总结性汇报之前必须先读完这一份（owner 2026-11-03 定的规矩，D59）。记账（欠账表、交接页、规格）不是汇报，不用按这个来；但凡要发给 owner 看的成段文字，都照这个标准。
> 怎么变短：反面例子只留一句结论，不重演全过程。

## 为什么有这份文档

2026-11-03 连着三轮汇报 owner 看不懂：满篇「引擎化」「门禁」「金样集」没有一句人话，还带着「蒸馅」（错字）和「一步都不准」（语病，本想说「一毫秒都不会更准」）。换成拿真实例子从头走一遍的讲法后，他说「比之前好很多」。本文档就是把那次换的讲法固化成规矩。

看不懂的病根三条：

1. **写给同行的话没翻译。**「管线」「回归」「消融」是工程师的口头禅，对 owner 是密码。
2. **用罗列代替讲解。**表格、编号、五层四件套——排得整整齐齐是写的人方便，不是读的人明白。
3. **一次塞太多。**现状、方案、验收、排期挤在一段里，每样只讲半截，于是每样都够不着。

## 怎么写：六条规矩

1. **先例子，后概念。**讲任何东西，先拿一个真实例子（真课、真句、真数字）从头走到尾，再给事情起名字。没有例子，就不许出现新名词。
2. **行话出现一个，当场用人话解释一个。**高频的见文末对照表；表里没有的新词，第一次出现就得带解释，不解释不许写。
3. **一次说清一件事。**一段汇报一个主题。现状、方案、要拍的板，分开说透；说不透的砍掉，下次单独说。
4. **叙事为主，表格只装真正的并列数据。**「五层、四件套、A 到 E」这种编号罗列是给写的人省事的；读的人需要的是顺序和因果。
5. **数字要有落点。**不写裸的「82/89」，写「89 句里 82 句开头完整」。数字脱离了它量的是什么，等于没有。
6. **汇报写给 owner，档案写给仓库。**工程细节进 `docs/handoff.md`、`docs/architecture.md`；汇报里只留 owner 做决定需要知道的。

## 总结性汇报的编排

按这个顺序，缺哪段跳过哪段：

1. **头一句说结论**：干成了什么、现在能用了什么。不从过程讲起——过程他没有参与，结论才是他要的入口。
2. **要他理解的，拿一个例子走一遍**：真实材料进去，每一步的输入和输出，为什么需要这一步。走完例子再给这件事起名字。
3. **要他拍板的，摆选项和推荐**：一次一件，推荐放前面，理由两三条说完。
4. **收尾落到接下来**：做什么、归谁、多久——和 CLAUDE.md「怎么说话」的收尾规矩是同一条。

`/wrap` 收尾的五句话是上下文压缩前的专用格式，照 `.zcode/commands/wrap.md` 走，不按本文档展开。

## 发出之前：自检，必要时复核

- **完整通读一遍再发。**「蒸馅」和「一步都不准」都是没通读就发出去的。通读时问三个问题：有没有没解释的行话？有没有裸数字？有没有一段塞了两件事？
- **读着卡壳的地方，就是没写明白的地方。**回去重写那一段；在卡壳处加个括号解释是糊弄，不算修好。
- **长汇报（两屏以上）或拿不准的，先复核再发**：派一个只读的 agent，只给它一个任务——「你是第一次听说这个项目的人，读这份汇报，指出哪几段看不懂」；按它挑出的地方改完再发给 owner。复核发生在发出之前，不是发了再改。

## 高频行话对照表（随用随补）

| 行话 | 人话 |
|---|---|
| 引擎化 | 把分工序的几段代码收进一个有统一入口的盒子，盒子有版本号、带自动打分 |
| 管线 / 流水线 | 几个程序按顺序接力，上一个的输出是下一个的输入 |
| 回归测试 | 改完代码，把以前出过对错的老考卷重考一遍，确认没改坏 |
| 金样集 | 一份带标准答案的考卷，锁起来不许改，专门用来发现退步 |
| 门禁 | 一道自动检查，不过就不许合入或发布 |
| 消融实验 | 把系统的一个部件故意拿掉，看掉多少分，量化这个部件值多少 |
| 对上率 | 语音识别认出的词里，和讲稿对得上的比例 |
| 蒸馏 | 从人的判断里提炼出机器能照做的规则（「蒸馅」是错字，2026-11-03 真写出来过） |
